## 3. Local development

> **Do not run a dev server on the user's behalf.** The user runs the app themselves in Visual Studio 2022 with Hot Reload. Make your code changes and let them reload.

Useful commands from the repo root (`C:/Cursor_Files/drawingregisterMJ`):

```powershell
# Restore and build
dotnet restore
dotnet build drawingregisterMJ.sln -c Debug

# Run tests
dotnet test

# Clean
dotnet clean
```

XAML edits and most C# edits are picked up by Hot Reload without a rebuild. Changes to `.csproj`, new files, or assembly-level edits require a rebuild.

## 4. Code style and conventions

- **Language:** C# 12 with nullable reference types enabled (`<Nullable>enable</Nullable>`).
- **UI:** WPF + MVVM. Prefer `ObservableProperty` / `RelayCommand` from `CommunityToolkit.Mvvm` over hand-written `INotifyPropertyChanged`.
- **Logging:** Use the existing Serilog logger. Don't add `Console.WriteLine` for diagnostics.
- **PDFs:** Read with PdfPig, write/compose with QuestPDF. Don't add a second PDF library.
- **No new top-level dependencies** without asking the user — every extra package affects the installer size (currently ~83 MB self-contained).
- **Comments:** Only when the *why* isn't obvious. No boilerplate XML doc comments on private members.
- **File naming:** PascalCase for `.cs` and `.xaml`, matching the class name. Dialogs end in `Dialog.xaml`.
- **Commit messages:** Conventional-ish prefixes are in use: `feat:`, `fix:`, `chore:`, `release:`. Keep them short and imperative. Look at `git log --oneline` for examples before writing yours.

## 5. Testing

- Test project: `DrawingRegister.App.Tests/` (xUnit).
- Run with `dotnet test` from the repo root.
- When adding file-operation or PDF-export logic, add tests alongside `FileOperationsExportTests.cs`.
- There is no integration-test harness for the WPF UI itself — manual verification by the user covers UI behavior.

## 6. Release process (critical — read carefully)

This is the single most important section of this document. End users get updates through Velopack, which reads GitHub releases. A broken release breaks auto-update for everyone.

### 6.1 Files that must change for every release

For version `X.Y.Z`:

**a) `DrawingRegister.App/DrawingRegister.App.csproj`** — three properties:
```xml
<Version>X.Y.Z</Version>
<AssemblyVersion>X.Y.Z.0</AssemblyVersion>
<FileVersion>X.Y.Z.0</FileVersion>
```

**b) `DrawingRegister.App/MainWindow.xaml`** — the `Title` attribute:
```xml
Title="DOCUMENT AND DRAWING REGISTER vX.Y.Z" Height="800" Width="1200"
```

**c) `AboutDialog.xaml`** — do **not** edit. The hardcoded `Version 1.0.0` is overwritten at runtime from `UpdateService.CurrentVersion`, which reads the assembly version.

### 6.2 Authentication: GitHub Personal Access Token

`vpk upload github` needs a GitHub PAT with the **`repo`** scope (Classic PAT) or, for a fine-grained token, the following permissions on `kyle93afc/drawingregisterMJ`:

- **Contents:** Read and write
- **Metadata:** Read-only (automatic)

**Never commit, hardcode, or log the token.** The user provides it at release time. If the token is exposed in shell history or in a file, tell the user immediately so they can rotate it at https://github.com/settings/tokens.

When using the GitHub CLI:

- Prefer `gh auth login --web` when the user is present rather than asking them to paste a token into chat.
- **Never run `gh auth token`** unless the user explicitly asks for it. That command prints the raw token to stdout.
- Treat any command output containing a token as a security incident and tell the user to rotate it immediately.
- `gh auth status` is safe for checking whether CLI auth is valid.

If you're running unattended and can't prompt the user, **stop before the upload step** and surface a clear request for the token rather than trying to proceed without it.

### 6.3 Release steps (PowerShell, run from repo root)

Replace `X.Y.Z` with the real version. Keep the version consistent across **all four places**: csproj, MainWindow title, `vpk pack --packVersion`, and `vpk upload --tag`.

```powershell
cd C:/Cursor_Files/drawingregisterMJ

# 1. Build self-contained, Release, win-x64
dotnet publish DrawingRegister.App -c Release --self-contained -r win-x64 -o ./publish

# 2. Package with Velopack
vpk pack --packId "DrawingRegister" --packVersion "X.Y.Z" --packDir ./publish --mainExe "DrawingRegister.App.exe"

# 3. Upload to GitHub (creates a draft release and uploads assets)
vpk upload github --repoUrl "https://github.com/kyle93afc/drawingregisterMJ" --tag "vX.Y.Z" --token "$env:GITHUB_TOKEN"

# 4. Publish the release and add notes
gh release edit vX.Y.Z --repo kyle93afc/drawingregisterMJ --draft=false --title "vX.Y.Z" --notes "Short, user-facing description of what changed"
```

Prefer setting the token as an env var (`$env:GITHUB_TOKEN = "ghp_..."`) so it doesn't appear on the command line or in shell history.

### 6.4 Commit and push the version bump

Commit the csproj + MainWindow.xaml bump **before** running `vpk upload` so the git state matches what's shipping:

```powershell
git add DrawingRegister.App/DrawingRegister.App.csproj DrawingRegister.App/MainWindow.xaml
git commit -m "release: vX.Y.Z - <short summary>"
git push origin working-version
```

### 6.5 Release checklist

Run through this top to bottom — do not skip steps, do not reorder.

- [ ] Confirm which commit on `working-version` contains the changes you are shipping
- [ ] Cross-check the latest remote tag/release before bumping so you don't skip or duplicate a version (`git ls-remote --tags origin`, `gh release list`, or equivalent)
- [ ] Pick the new version number (patch for fixes, minor for features, major for breaking changes)
- [ ] Check `git status --short` and make sure unrelated untracked files are not accidentally included in the release commits
- [ ] Edit `DrawingRegister.App.csproj` — `<Version>`, `<AssemblyVersion>`, `<FileVersion>`
- [ ] Edit `MainWindow.xaml` — `Title="DOCUMENT AND DRAWING REGISTER vX.Y.Z ..."`
- [ ] Commit the feature/fix work separately if useful, then commit the version bump in its own `release:` commit
- [ ] `git commit` the bump with a `release: vX.Y.Z - ...` message
- [ ] Push `working-version` before `vpk upload` so the remote tag points at a commit that already exists on GitHub
- [ ] `dotnet publish DrawingRegister.App -c Release --self-contained -r win-x64 -o ./publish`
- [ ] `vpk pack` with matching `--packVersion X.Y.Z`
- [ ] Obtain valid GitHub auth for both `vpk` and `gh` (PAT or `gh auth login`; do not guess, do not reuse a stale token)
- [ ] `vpk upload github` with matching `--tag vX.Y.Z`
- [ ] `gh release edit vX.Y.Z --draft=false --title "vX.Y.Z" --notes "..."`
- [ ] Verify the release is visible and marked Latest at https://github.com/kyle93afc/drawingregisterMJ/releases
- [ ] Confirm Velopack assets (`DrawingRegister-X.Y.Z-full.nupkg`, `DrawingRegister-X.Y.Z-delta.nupkg`, `RELEASES`, `releases.win.json`, `DrawingRegister-win-Setup.exe`, `DrawingRegister-win-Portable.zip`) are all attached to the release

### 6.6 Release pitfalls to watch for

- **Version drift.** If the csproj was previously bumped but the release didn't actually publish, you may find the working tree already at `X.Y.Z` while GitHub's latest is `X.Y.(Z-1)`, or the other way around. Always cross-check `git log`, the csproj `<Version>`, and `gh release list` before bumping.
- **Remote vs local tags.** Local tags may be stale. Before picking the next version, check the remote tags/releases, not just `git tag`.
- **Tag vs commit mismatch.** `vpk upload` creates the tag on GitHub. Make sure your local commit for the version bump is pushed before or right after the upload so `v X.Y.Z` on GitHub points at the intended commit.
- **Full package size.** The `-full.nupkg` is roughly 80 MB. If your build output is dramatically smaller, something is wrong with the publish — check that `--self-contained` and `-r win-x64` were both passed.
- **Draft releases.** `vpk upload` may leave the release as a draft. Always finish with `gh release edit --draft=false` or users won't see the update.
- **`gh` auth.** `gh release edit` needs its own auth (`gh auth status`). That's separate from the PAT used by `vpk upload`. Don't assume one covers the other.
- **Token exposure.** Avoid any command that prints credentials to stdout. If a token is revealed in terminal output, tell the user immediately and have them rotate it.
- **Unrelated working tree noise.** This repo may contain user-owned untracked files or local instruction files. Do not stage or clean them unless the user explicitly asks.

## 7. What not to do

- Don't run the dev server / debug session for the user — they do that themselves in Visual Studio.
- Don't add new NuGet packages without asking.
- Don't edit `AboutDialog.xaml`'s hardcoded version string.
- Don't push directly to `main` — this project ships from `working-version`.
- Don't commit `publish/`, `bin/`, or `obj/` directories.
- Don't hardcode, log, or commit the GitHub PAT, even in example commands.
- Don't run `gh auth token` as part of a normal release flow.
- Don't use `git push --force` or `git reset --hard` on shared branches without explicit user approval.

## 8. When in doubt

- The canonical release procedure is Section 6 of this file. If `CLAUDE.md` or `RELEASE_INSTRUCTIONS.md` ever disagree with it, this file wins and the others should be updated to match.
- If you encounter an unexpected repo state (detached HEAD, uncommitted changes you didn't make, a tag pointing at the wrong commit), **stop and ask the user** instead of trying to clean it up automatically.
